# 服务挂了怎么办

> 一部分：`tools/watchdog.py` 是怎么兜底的。

---

## 服务挂了怎么办（watchdog.py）

**这是这个项目里最容易被忽略、但最要命的一块。**

### 问题

服务挂了没人拉，就再也起不来了。

如果重启这件事交给服务自己干：

```
服务 A 让服务 B 重启
  → B 死
  → A 跟着死（如果同一个进程树）
  → 没人再把它拉起来
```

死锁。**而这个死锁恰好在最要紧的时候发生：你人在外面，改完东西需要重启验证，结果一重启整个系统就没了。**

### 它现在守护谁

**atrium** —— 那个接聊天平台、当前台的门。

```
以前守护的是 AstrBot，那套已经废弃了（见上面「以前的 AstrBot 方案」）。
守护逻辑没变，只是换了个目标。
```

### 做法

一个**不在被守护进程树下面**的独立进程。它同时干两件事，这两条是**独立的线**：

**线一：被动听请求**

```
<桥目录>/restart.request      ← 谁要重启，往这里写一行
<桥目录>/restart.result       ← 守护把结果写回来
```

用 Windows 的目录变更通知（`ReadDirectoryChangesW`）监听，**内核推事件，没事件时零开销**。

**线二：主动体检**

**这一条才是"守护"的真正含义。**

第一版只做了线一。当时以为够了，直到有人点破：

> 服务自己崩了、没人写 `restart.request`，它就干看着。

**对。没人请求的时候服务崩了，那才是最需要它的时候。**

### 怎么判断"活着"

atrium 不监听端口（它主动连平台出去），所以**没有端口可以查**。

改成心跳：

```
atrium 起来后，每 10 秒写一次 ~/.atrium/alive.json
    {"pid": 3684, "ts": 1793751104.16, "uptime": 10.0}

看门狗每 30 秒读一次：
    超过 60 秒没更新 → 判定挂了
```

**为什么不查进程在不在：** 进程可能在，但已经卡死了（死锁、卡在网络请求）。
心跳不写了就是真的不行了 —— 比看进程表准。

实测（杀掉 atrium 不写任何请求文件）：

```
[08:13:04] 发现它不活了（心跳 71 秒没更新），自动拉起
[08:13:04] 拉起了：... -m atrium.cli run
[08:13:04]   PYTHONPATH 加了 D:\Project\atrium
[08:13:06] 重启成功
```

**全程没人请求，2 秒就回来了。**

### 拉起的时候带上 PYTHONPATH

```
看门狗通常跟 remote-dispatch 放在一起
    ↓
而 atrium 是另一个仓库
    ↓
从这儿跑 python -m atrium.cli run 直接 ModuleNotFoundError
```

**所以起进程时自动把 atrium 目录塞进 PYTHONPATH。**

默认取 `DSH_ATRIUM_DIR`，或者跟 remote-dispatch 平级的 `../atrium`。

### 三条自保的规矩（这些不是可选项）

**注意：这三条是 watchdog 自己的约束，跟「安全」那节的防护不是一回事。**
放在这里是因为它们解决的是「守护进程别把事搞更大」。

| 规矩 | 为什么必须有 |
|---|---|
| **冷却 5 分钟** | 以前因为反复重启被平台风控过。重启太频繁会把账号搞出事，这条就是挡这个的 |
| **连续失败 3 次就停手** | 免得变成"起了就崩、崩了再起"的死循环，把机器拖死。停手后写 `.stuck` 文件，等人来看 |
| **不乱杀** | 只杀命令行里带 `atrium.cli` 的 python 进程。用户可能还开着别的 Python 程序，那些不能碰 |

### 手动重启要能绕过冷却

冷却期是防"自动反复重启"的，但**用户手动点重启的时候，他知道自己在干什么。**

所以 `restart.request` 支持一个 `force` 字段：

```json
{"who": "桌面端", "reason": "用户点了重启", "force": true}
```

`force: true` 会跳过冷却和 `.stuck`，立刻重启。

实测（2026-11-04 就撞过这个）：刚重启完又崩了，冷却期让看门狗干看着不动，得等 5 分钟 —— 那 5 分钟里服务是死的，用户只能干等。

### 用起来

```bash
# 启动（pythonw 无窗口）
pythonw tools/watchdog.py

# 调试时带控制台
python tools/watchdog.py
```

**环境变量（可选）：**

```bash
set DSH_WATCHDOG_CMD="C:\Python312\python.exe" -m atrium.cli run
set DSH_WATCHDOG_DEAD_AFTER=60      # 心跳多久没更新算挂
set DSH_ATRIUM_DIR=D:\Project\atrium
```

**让它开机自启**（Windows）：

```powershell
schtasks /create /tn "dsh-watchdog" /tr "pythonw.exe C:\path\to\tools\watchdog.py" /sc onlogon /rl highest
```

### 一次改写的记录

第一版监听是用 `ctypes` 直接调 `ReadDirectoryChangesW` 写的。

**实测：往目录里写文件，守护进程 CPU 一直是 0，没有任何反应。** 调用卡在里面不返回，参数拼错也不报错。

**ctypes 拼 Win32 结构太容易出无声的错** —— 后来改回 ctypes 是因为不想多一个 pywin32 依赖，
但加了兜底：目录监听起不来就退化成轮询（见下面「关于要不要轮询」）。

### 关于"要不要轮询"

合理的组合是：**听请求用事件，查死活用低频轮询。**

- 听请求：可以事件驱动，零开销，就用事件
- 查死活：没有事件源，只能轮询——但 30 秒一次可以忽略

**不是全都轮询，也不是全都事件。** 一开始两样都想要事件，结果听请求那半确实该用事件，查死活那半根本没法事件。
